---
title: Arithmetic and comparisons
description: Checked arithmetic, exponentiation, modular arithmetic, comparison, boolean, bitwise, and conversion operations on Expr values, with solc 0.8 panic semantics.
---

All arithmetic in evs is **checked**, matching solc 0.8 semantics exactly: overflow reverts with `Panic(0x11)`, division by zero with `Panic(0x12)`. Operations are methods on `Expr`, with the operand domain enforced by the type system.

## The operation surface

| Group              | `Expr` methods                                  | Operands                                       | Result          |
| ------------------ | ----------------------------------------------- | ---------------------------------------------- | --------------- |
| Checked arithmetic | `add` `sub` `mul` `div` `mod`                   | numeric (`uintN` / `intN`), same type          | same type       |
| Exponentiation     | `pow`                                           | numeric base; unsigned exponent (any `uintN` or literal) | base type |
| Modular arithmetic | `addmod` `mulmod`                               | `uint256` (value, operand, modulus)            | `Expr<'uint256'>` |
| Ordering           | `lt` `gt` `lte` `gte`                           | numeric, same type                             | `Expr<'bool'>`  |
| Equality           | `eq` `neq`                                      | any word type, same type                       | `Expr<'bool'>`  |
| Boolean            | `and` `or` `not`                                | `bool`                                         | `Expr<'bool'>`  |
| Bitwise            | `bitAnd` `bitOr` `bitXor` `bitNot`              | `uintN` / `bytesN`, same type                  | same type       |
| Shifts             | `shl` `shr`                                     | value `uintN` / `intN` / `bytesN`; shift amount `uint256` | same as value |
| Conversions        | `toUint` `toInt` `asAddress` `asUint256` `asBytes32` | see [Conversions](#conversions)          | target type     |

Every method (except the conversions) also exists as a free function on the builder — `s.add(a, b)`, `s.lt(a, b)`, `s.shl(a, bits)`, `s.pow(base, e)`, `s.mulmod(a, b, n)`, and so on — for literal-left cases like `s.sub(100n, x)`. At least one operand of a free function must be an `Expr`; two plain literals throw `EvsTypeError` at recording (type one with `s.lit`). The exceptions are `addmod` / `mulmod`, whose operands are always `uint256` (all-literal calls simply fold), and `pow` and the shifts, whose left operand must be an `Expr` (its type is the result type).

Right-hand operands accept literals via [`IntoExpr` coercion](/guides/values-and-types/): `x.add(1n)`, `tick.lt(0n)`, `flag.and(true)`.

`eq`/`neq` also work on memref types (`string`, `bytes`, `T[]`, structs) as **hash equality**: `a.eq(b)` is recorded as `s.keccak256(a).eq(s.keccak256(b))`. For `string`/`bytes` that is byte-for-byte equality (the raw bytes are hashed, exactly like Solidity's `keccak256(bytes(a)) == keccak256(bytes(b))` idiom); for arrays and structs it is element-wise equality through their standard `abi.encode` (never the packed form, which is ambiguous for adjacent dynamic values). Both operands must have the same evs type — a word never compares with a memref, and `string` never compares with `bytes` or `string[]` — and the right-hand side takes the usual literals (`symbol.eq('WETH')`, `fees.neq([500n, 3000n])`). It costs two keccaks plus memory reads per comparison, so hoist a hash you compare repeatedly into one `s.keccak256(...)` value. Boolean `and`/`or` are **eager**, not short-circuiting: both sides are already-computed values by the time you combine them. For conditional execution, use `s.if` ([control flow](/guides/control-flow/)).

## Checked semantics

| Condition                                                       | Revert        |
| --------------------------------------------------------------- | ------------- |
| `add` / `sub` / `mul` result out of range for the operand type  | `Panic(0x11)` |
| `div` / `mod` by zero                                           | `Panic(0x12)` |
| signed division of the type's minimum value by −1               | `Panic(0x11)` |
| `pow` result out of range for the base type                     | `Panic(0x11)` |
| `addmod` / `mulmod` with a zero modulus                         | `Panic(0x12)` |
| checked narrowing out of range (`toUint` / `toInt` / `asAddress`) | `Panic(0x11)` |

Checks run at the operand type's width, not at 256 bits: a `uint64` addition overflows at 2^64. The signed-division edge case is handled explicitly — the EVM's `SDIV` silently wraps `−2^255 / −1`, but evs (like solc) reverts with `Panic(0x11)`.

Panics surface as standard `Panic(uint256)` reverts, which viem decodes natively; `explainRevert` explains the code and lists the candidate sites in your script that can raise that panic. See [errors and debugging](/guides/errors-and-debugging/).

Shifts follow Solidity: they are **unchecked**, with the result re-canonicalized to the operand's width — bits shifted out of a `uint8` lane are simply dropped, never a panic. `shr` is a logical shift for `uintN` and `bytesN` and an arithmetic shift (`SAR`) for `intN`: it rounds toward negative infinity, exactly like Solidity's `>>` on signed integers (`-3 >> 1 == -2`). `shl` on `intN` re-sign-extends from the width, so `int8(127).shl(1)` is `-2`. Note that `shr` on `bytesN` shifts within the full 256-bit word and re-masks to the left-aligned lane.

## Exponentiation

`a.pow(e)` is Solidity's `a ** e` under checked arithmetic: the exact power, `Panic(0x11)` when it does not fit the **base's** type, and `0 ** 0 == 1`. The result has the base's type; the exponent is unsigned — a non-negative literal or an `Expr` of any `uintN` width (a signed exponent is a type error, as in Solidity). Signed bases follow the asymmetric range exactly: `(-2) ** 7` is `-128` and fits `int8`, `2 ** 7` overflows it, and `(-1) ** e` never overflows whatever `e` is.

```ts
import { evscript, t } from '@maxencerb/evs';

const scale = evscript({ name: 'scale', args: [t.uint256, t.uint8] }, (s, amount, decimals) => {
  // 10 ** decimals — a literal base compiles to one bound check (decimals ≤ 77) and one EXP
  const unit = s.lit(t.uint256, 10n).pow(decimals);
  // a literal exponent compiles to one check on the base (amount ≤ ⌊(2^256 − 1)^(1/3)⌋) and one EXP
  const cubed = amount.pow(3n);
  return s.return({ whole: amount.div(unit), cubed });
});
```

What it costs depends on what is known at recording time. A **literal base** (`s.lit(t.uint256, 2n).pow(e)`) is one comparison against the largest exponent that fits plus one `EXP` — for `2 ** e` on `uint256` exactly solc's `e > 255` check. A **literal exponent** (`x.pow(3n)`) is one range check on the base against the precomputed integer root of the type's bound, then one `EXP`. When both are runtime values evs runs solc's square-and-multiply loop, with an overflow check before every squaring: at most 7 iterations (an exponent above 255 with a base of magnitude ≥ 2 panics straight away), about 1,100 gas in the worst case against roughly 100 for the literal-base and literal-exponent forms, and a single `EXP` when the base is `0`/`±1` or the exponent is `0`.

## Modular arithmetic

`a.addmod(b, n)` and `a.mulmod(b, n)` are Solidity's `addmod(a, b, n)` / `mulmod(a, b, n)`: `(a + b) % n` and `(a * b) % n` computed at **full precision** — the intermediate sum or product is never truncated to 256 bits, so `mulmod(x, y, p)` is the right tool for modular arithmetic over a large prime where `x.mul(y).mod(p)` would overflow. They are `uint256`-only (value, operand and modulus), and a zero modulus reverts with `Panic(0x12)`, like `div` / `mod`. A nonzero literal modulus drops that runtime check, as a literal divisor does for `div` / `mod`.

```ts
import { evscript, t } from '@maxencerb/evs';

const P = 21888242871839275222246405745257275088548364400416034343698204186575808495617n;

const field = evscript({ name: 'field', args: [t.uint256, t.uint256] }, (s, x, y) => {
  const prod = x.mulmod(y, P); // (x * y) mod P, no 512-bit overflow
  const sum = s.addmod(x, y, P);
  return s.return({ prod, sum });
});
```

## Signedness selects the comparison

`lt`/`gt`/`lte`/`gte` compile to the EVM's unsigned `LT`/`GT` for `uintN` and to signed `SLT`/`SGT` for `intN`, chosen from the **static type** of the operands (`lte`/`gte` are `ISZERO` of the opposite strict comparison). You never pick an opcode; declaring the right type is enough:

```ts
import { evscript, t } from '@maxencerb/evs';

const tickSide = evscript({ name: 'tickSide', args: [t.int24] }, (s, tick) => {
  const isNegative = tick.lt(0n); // int24 → SLT: −100 < 0 is true
  // literal-left subtraction via the free function; checked, so negating the
  // int24 minimum value would revert with Panic(0x11)
  const magnitude = s.select(isNegative, s.sub(0n, tick), tick);
  return s.return({ isNegative, magnitude });
});
```

The same selection logic keeps signed values canonical everywhere: `intN` words are sign-extended, and every operation preserves that invariant.

## One type per operation

Both operands must have the **same** evs type. The TS surface enforces it (the right-hand side of `a.add(b)` must be `IntoExpr` of `a`'s type), and the recorder double-checks at recording time — mixing two `Expr`s of different types throws `EvsTypeError` naming both types. There are no implicit widenings.

This does not compile:

```ts nocheck
import { evscript, t } from '@maxencerb/evs';

const mix = evscript(
  { name: 'mix', args: [t.uint128, t.uint256] },
  // TS error: Expr<'uint256'> is not assignable to IntoExpr<'uint128'>
  (s, a, b) => s.return({ sum: a.add(b) }),
);
```

Convert explicitly instead:

```ts
import { evscript, t } from '@maxencerb/evs';

const mix = evscript(
  { name: 'mix', args: [t.uint128, t.uint256] },
  (s, a, b) => s.return({ sum: a.toUint(t.uint256).add(b) }),
);
```

## Conversions

- **`toUint(target)` / `toInt(target)`** — numeric to numeric. Widening is free; narrowing is range-checked and reverts with `Panic(0x11)` when the value does not fit. Cross-signedness conversions are range-checked the same way: `uint256` to `int256` panics for values of 2^255 and above.
- **`asAddress()`** — on `Expr<'uint256'>` or `Expr<'bytes32'>`; checked that the high 96 bits are zero (`Panic(0x11)` otherwise).
- **`asUint256()` / `asBytes32()`** — free reinterpretation between `bytes32` and `uint256` (both occupy the full word; no check, no cost).

```ts
import { evscript, t } from '@maxencerb/evs';

const casts = evscript(
  { name: 'casts', args: [t.uint256, t.bytes32] },
  (s, x, w) => {
    const small = x.toUint(t.uint64); // checked narrowing: Panic(0x11) if x ≥ 2^64
    const wide = small.toUint(t.uint256); // widening: free
    const signed = x.toInt(t.int256); // checked: Panic(0x11) if x ≥ 2^255
    const addr = w.asAddress(); // checked: high 96 bits must be zero
    const word = w.asUint256(); // free reinterpret
    return s.return({ small, wide, signed, addr, word });
  },
);
```

## Literal folding at recording time

Pure operations whose operands are all statically known fold at recording — no bytecode is emitted for them:

```ts
import { evscript, t } from '@maxencerb/evs';

const fees = evscript({ name: 'fees', args: [t.uint256] }, (s, amount) => {
  // all operands statically known → folds at recording into the constant 60
  const feeBps = s.lit(t.uint256, 30n).mul(2n);
  const fee = amount.mul(feeBps).div(10_000n);
  return s.return({ fee });
});
```

If a fold would **certainly panic** — `s.lit(t.uint8, 250).add(10n)`, a literal division by zero, an out-of-range `toUint` of a known value — recording throws `EvsTypeError` (code `CERTAIN_PANIC`) at that line rather than compiling a guaranteed revert. If a guaranteed runtime panic is what you actually want, route one operand through a cell so its value is no longer statically known: `s.let(t.uint256, x).get()`, and use the result (return it, or feed it to something that is kept). A result nothing reads is dead code: `compile()` drops it, its panic included (see [Unused results do not revert](/guides/testing-scripts/#unused-results-do-not-revert)).

## Worked example: share of supply in basis points

```ts
import { evscript, t } from '@maxencerb/evs';
import { erc20Abi } from 'viem';

const shareOfSupply = evscript(
  { name: 'shareOfSupply', args: [t.address, t.address] },
  (s, token, owner) => {
    const bal = s.read({
      address: token,
      abi: erc20Abi,
      functionName: 'balanceOf',
      args: [owner],
    });
    const supply = s.read({ address: token, abi: erc20Abi, functionName: 'totalSupply' });
    // bal * 10_000 / supply — mul reverts with Panic(0x11) on overflow,
    // div with Panic(0x12) if totalSupply() returns zero
    const bps = bal.mul(10_000n).div(supply);
    const isWhale = bps.gte(100n); // ≥ 1% of supply (uint256 → unsigned comparison)
    return s.return({ bps, isWhale });
  },
);
```

## Not supported yet

A few things Solidity can do have no `Expr` operation in this version. Each has a workaround:

| Missing                                                       | Workaround                                                                                                   |
| ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `unchecked { }` / wrapping `*`                                | build it from full-precision `mulmod` / `addmod` ([below](#wrapping-multiplication))                        |
| 512-bit `mulDiv` (Uniswap's `FullMath`)                       | `a.mul(b).div(d)` reverts once `a * b` passes 2^256, even when the quotient fits; return the operands and finish on the client |
| `address` ordering, `uint160(addr)`, `address(uint160(x))`    | type the address as `uint160` at the ABI boundary ([below](#ordering-addresses-and-create2))                 |
| `bytesN` ↔ `uintN` other than `bytes32` ↔ `uint256`, byte access, slicing, `bytes32` → `string` | declare the value as `bytes32` / `uint256` in your ABI fragment and shift, or decode it on the client (see [legacy `bytes32` metadata](/guides/calls/#legacy-bytes32-metadata)) |

### Wrapping multiplication

`a * b mod 2^256`, what solc emits as a bare `MUL` inside `unchecked { }`, splits into 128-bit
halves whose partial products `mulmod` and `addmod` compute without overflow. It costs about 300
gas per multiply instead of a few, so keep it to the places that need wrapping semantics (hash
mixing, Newton iterations ported from Solidity):

```ts
import { evscript, t, type Expr } from '@maxencerb/evs';

const LOW_128 = (1n << 128n) - 1n;
const TWO_128 = 1n << 128n;
const MAX_UINT256 = (1n << 256n) - 1n;

/** a * b mod 2^256: Solidity's unchecked multiply, from full-precision mulmod / addmod. */
function wrappingMul(a: Expr<'uint256'>, b: Expr<'uint256'>): Expr<'uint256'> {
  const aLo = a.bitAnd(LOW_128);
  const aHi = a.shr(128n);
  const bLo = b.bitAnd(LOW_128);
  const bHi = b.shr(128n);
  // aLo * bLo < 2^256 − 1, so reducing it modulo 2^256 − 1 keeps the exact product
  const low = aLo.mulmod(bLo, MAX_UINT256);
  // only the low 128 bits of the cross terms survive the shift into the high half
  const cross = aLo.mulmod(bHi, TWO_128).addmod(aHi.mulmod(bLo, TWO_128), TWO_128);
  const high = low.shr(128n).addmod(cross, TWO_128);
  return high.shl(128n).bitOr(low.bitAnd(LOW_128));
}

const square = evscript({ name: 'square', args: [t.uint256] }, (s, x) =>
  s.return({ wrapped: wrappingMul(x, x) }),
);
```

### Ordering addresses and CREATE2

An `Expr<'address'>` supports `eq` / `neq` only, and no conversion turns it into a number. The
ABI encodes an `address` and a `uint160` as the same word, so declare the address as `uint160`
where it enters the script: in the script's `args` (the caller passes `BigInt(address)`), or as
the output type in your own ABI fragment for a getter such as `token0()`. A `uint160` sorts with
`lt`, and `.toUint(t.uint256).asAddress()` turns it back into an address. The same pieces derive
a CREATE2 address, here a Uniswap V3 pool:

```ts
import { evscript, t } from '@maxencerb/evs';

const FACTORY = '0x1F98431c8aD98523631AE4a59f267346ea31F984';
const POOL_INIT_CODE_HASH = '0xe34f199b19b2b4f47f68442619d555527d244f78a3297ea89325f843f87b8b54';

const poolAddress = evscript(
  { name: 'poolAddress', args: [t.uint160, t.uint160, t.uint24] }, // tokens passed as BigInt(address)
  (s, tokenA, tokenB, fee) => {
    const aFirst = tokenA.lt(tokenB); // Uniswap's token0 < token1 ordering
    const token0 = s.select(aFirst, tokenA, tokenB).toUint(t.uint256).asAddress();
    const token1 = s.select(aFirst, tokenB, tokenA).toUint(t.uint256).asAddress();
    const salt = s.keccak256(token0, token1, fee); // keccak256(abi.encode(token0, token1, fee))
    const hash = s.keccak256(
      s.encodePacked(
        s.lit(t.bytes1, '0xff'),
        s.lit(t.address, FACTORY),
        salt,
        s.lit(t.bytes32, POOL_INIT_CODE_HASH),
      ),
    );
    const pool = hash.asUint256().bitAnd((1n << 160n) - 1n).asAddress(); // the low 20 bytes
    return s.return({ token0, token1, pool });
  },
);
```
