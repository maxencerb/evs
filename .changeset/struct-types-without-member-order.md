A `t.struct` and an ABI tuple with the same members are now the same type under every type checker, whatever order the members are written in. The types used to recover a struct's member order from a union, and the order of a union belongs to the checker: TypeScript 5 and 6 keep the order in which a program first mentions each member, TypeScript 7, `bun check` and tsrs sort. So `t.array(t.struct({ token: t.address, amount: t.uint256 }))` passed to an ABI `tuple[](address token, uint256 amount)` parameter was a compile error on TypeScript 7 (and on 5 and 6 once the program mentioned `amount` before `token`), although the script recorded and compiled. An ABI `tuple[]` result did not fit an `s.fn` parameter or an `s.let` typed with the hand-written struct either, on any version. The `components` of a fully named tuple type is now the exported `NamedComponents`: its members in no order, with their count, so a struct with a missing, extra or differently typed member is still a compile error. The member order is checked when the script is recorded, as before: a struct with the right members in another order type-checks and then throws `TYPE_MISMATCH`. A script's return record is typed the same way, without a count, which makes a wide one cheap to check: 300 return keys took 5.5 s of type-checking on TypeScript 6 and now take 0.14 s, and 1,000 keys take 0.16 s with an exact result. A tuple output of a `parseAbi` ABI with unnamed members (`returns ((uint256, address))`) is typed as the positional tuple it is; its handle used to collapse to an unusable type. Types only: the bytecode and the runtime behavior are unchanged. The types are now tested under TypeScript 5.5, 6 and 7, `bun check` and tsrs.
