'@maxencerb/evs': patch
---

Long and deep scripts no longer crash the compiler with `RangeError: Maximum call stack size exceeded`. A script whose values form a long chain (an accumulator updated by a JavaScript loop, `acc = acc.wrappingAdd(1n)` a few thousand times) now compiles, interprets and goes through `eliminateDeadCode` whatever its length: it used to fail from about 2,500 links in a fresh process, and to pass in a warm one, although such a script can be well within the size limit under `optimize`. Blocks (`s.if` branches, loop bodies, `s.fn` bodies) now nest at most 256 levels deep: one level more throws `EvsTypeError` (`UNSUPPORTED_V0`) from the builder call that opens it, where a deeper script used to overflow the stack while recording or in `compile()`. `deserializeIr` applies the same limit, and one of 256 levels to the tuples nested in a type, and names the JSON path, instead of overflowing on a deeply nested document; it also no longer slows down quadratically with the nesting depth.

An invalid IR that evs did not record itself (the result of `deserializeIr`, or an object written by hand) is now reported as your input and not as a bug in evs: `compile()`, `interpret()` and `eliminateDeadCode()` throw `EvsTypeError` (`TYPE_MISMATCH`) with the position of the offending statement, where they threw `EvsInternalError` asking for a bug report. `eliminateDeadCode()` now validates such an IR before running. The validation also rejects a call whose `gas` or `value` operand is one of the call's own outputs, which used to compile to bytecode reading a value that was never written.
