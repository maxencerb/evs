Close the remaining type shapes (#4): fixed-size arrays `T[N]`, two-level tuple arrays `tuple[][]`, arrays nested to any depth, and overloaded `view`/`pure` function resolution.

- **Fixed-size arrays** — `t.array(elem, N)` / the `'uint256[2]'` string form / `tuple[N]` descriptors, over any element (word, struct, dynamic, array). In memory a `T[N]` is laid out exactly like a `T[]` (length word always `N`), so `.length()`, `.at(i)`, `s.forEach`, `set`, cells and fn params reuse the dynamic-array machinery; only the ABI codec differs (no length word on the wire; static — inlined into the head — when the element is static). Literals must carry exactly `N` elements (`TYPE_MISMATCH` at recording — the static type stays a plain `readonly` array: an N-tuple type made TypeScript's literal inference exponential); `s.newArray(elem, N, { fixed: true })` allocates one from a literal length. `arrnew` gains an optional `fixed` field — additive, `irVersion` stays 1, old IR loads unchanged.
- **`tuple[][]` and deeper nesting** — every depth gate is gone (`core/types`, `abi/layout`, `abi/artifact`, `ir/validate`, `builder/expr`). The array decoder now keeps its loop state in heap-allocated frames (chained through scratch `0x20`), so the 16-item template budget no longer bounds nesting depth; encode already used memory frames. `uint256[][][]`, `string[][]`, `bytes[][]`, `tuple[][]`, `uint256[2][]`, `uint256[][2]`, … all work as script args, call args, outputs and returns, byte-exact vs viem and real solc on paris/shanghai/cancun.
- **Overload resolution** — `s.read`/`s.call`/`s.simulate` (and the `try*` variants) pick an overload by arity, then by per-argument compatibility (a staged handle by exact type, a host literal by JS shape — viem's `getAbiItem` rules); the output handle types follow the chosen overload via `FnForArgs`, the mirror of viem's `ExtractAbiFunctionForArgs`. Only a genuine tie (e.g. `f(uint8)` vs `f(uint256)` with a bare number) stays `UNSUPPORTED_V0`, with a message that says how to break it. `t.fromOutputs` accepts an overloaded name when every overload declares the same outputs.
- `s.newArray` slots of a composite element (`string`, `T[]`, `tuple`, `T[N]`) now start as the element's typed zero value instead of a null pointer, matching the interpreter — an element you never set encodes as its zero.
- Word-array literals that mix in an `Expr` element (`[x, 1n]`) are built element-wise instead of being rejected.
- `t.array(elem, N)` / `FixedLengthOf` / `PeelArraySuffix` / `FnForArgs` and the runtime helpers `peelArraySuffix` / `fixedLengthOf` / `isTupleTag` / `tupleArrayTag` are new. `ArrayType` keeps the exact dynamic literals (`T[]`, `T[][]`, `T[][][]`) and admits every other suffix chain (`T[N]`, `T[N][]`, `T[][N]`, deeper nesting) through ONE catch-all pattern `` `${string}[${string}` `` — a union of leaf-exact patterns made the full type-check ~6× slower, so the leaf of a fixed-size / 4+-deep string is validated at runtime only (`'foo[2]'` type-checks; its element is `never`; recording throws `TYPE_MISMATCH`). Concrete types stay exact literals and `ArrayElemOf` / `.at()` / `s.forEach` peel them exactly at any depth. `TupleType['type']` is `'tuple' | `tuple[${string}` ``.
- A tuple type written as a *string* (`'tuple'`, `'tuple[]'`) and a malformed array suffix (`uint256[0]`) are now `TYPE_MISMATCH` everywhere (they were `UNSUPPORTED_V0` in `layoutOf`); `UNSUPPORTED_V0` is reserved for the ambiguous-overload case and `t.fromOutputs` over differing overloads.
