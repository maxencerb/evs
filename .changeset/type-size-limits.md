Reject pathological types with coded errors. A type string with thousands of array suffixes (`'uint256' + '[]'.repeat(50000)`) passed to `t.array`, `t.struct`, `t.fromAbiParameter`, `t.fromOutputs`, a script argument or a `s.read` ABI used to overflow the host stack with a raw `RangeError`; it now throws `EvsTypeError` (`UNSUPPORTED_V0`) like any type nested deeper than four levels, validation is linear in the string length, and error messages quote such a type cut short. An ABI-static type of 2^32 bytes or more (`uint256[100000000][100000000]`, a struct of two `uint256[67108864]` members), or an array of such elements (`uint256[100000000][100000000][]`), is now `UNSUPPORTED_V0` too, from the `t` constructors, at recording for an argument or call output, and at the latest from `compile()` and `interpret()`: before, a size past 2^53 bytes reached the assembler and failed with `EvsInternalError` (`INTERNAL`), and a smaller one compiled into a script that could never run. `interpret()` charges zero-filled array elements (`s.newArray`, fixed-size zero values) to `maxSteps`, so a huge zero-fill throws `COMPILE_LIMIT` instead of exhausting the host heap.
