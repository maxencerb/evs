`DEPLOYLESS_RESULT_PREFIX` no longer warns for a leading `uint256` or `int256` that cannot start with byte `0xEF`. Such a value has to be at least `0xEF·2^248` (about 1.08e77) for a `uint256`, or below `-2^252` for an `int256`, so amounts and counts never trip it. `compile()` now bounds the bit width of the first returned value over the whole script, loops and `s.fn` calls included. `s.env('chainid' | 'blocknumber' | 'timestamp')`, lengths, `s.balance`, `s.codeSize`, widened narrower integers, and loop counters or running sums of such values no longer warn. A returned literal warns only when its first byte is `0xEF`, which fails every call. A `bytesN` still always warns. A `uint256`/`int256` from a script argument, a call output, a reinterpreted hash, `bitNot`, a signed bit operation or a left shift by a runtime amount also still warns. The warning now carries the `site` of the statement that computes the first returned value, so one amount (a sum of `balanceOf` reads, say) can be acknowledged without hiding the warning for a real hash. Its message is now specific to the type: it no longer calls a `uint256` "a hash 1 time in 256", and it says "an int256" instead of "a int256". Bytecode is unchanged.
