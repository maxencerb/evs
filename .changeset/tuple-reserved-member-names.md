'@maxencerb/evs': patch

A struct field named like a `Tuple` handle member no longer breaks the handle. Before, a field named `at` or `expr` replaced the `.at(i)` / `.expr()` methods: the code type-checked, then recording threw a raw `TypeError` (`h.expr is not a function`). A field named `toJSON`, `toString` or `valueOf` also disabled the matching staging trap. Now the handle member wins. A field named `at`, `expr`, `then`, `toString`, `valueOf`, `toJSON`, `constructor`, `__proto__` or any other `Object.prototype` member gets no field accessor and is read by position with `.at(i)`, and the `Tuple<C>` type drops these names too. Third-party ABIs with such members keep working. Field accessors now live on one shared prototype per tuple type instead of being created on every handle, so recording a struct-heavy script is faster and `Object.keys(handle)` is empty. A spread or `Object.assign` copy of a handle (`{ ...pos, owner }`) therefore holds no member: it was already a type error, and it now throws `TYPE_MISMATCH` where evs reads it as a tuple init or an `s.return` record, instead of zero-filling the members it omits.

`__proto__` is no longer accepted as a name. Before, `namedArg`, `t.struct`, `t.error`, `s.fn` params and `s.return` keys accepted it, and the value was then silently lost: assigning `__proto__` on a plain object replaces the prototype instead of storing the value. This affected viem's `readContract` result, `decodeScriptError` / `matchScriptError` args, `explainRevert` and `interpret().values`. Those names now throw `EvsTypeError` (`TYPE_MISMATCH`, `ERROR_DECL` or `ABI_SHAPE`, with a message that says `__proto__` is reserved and why), and so does a third-party struct with a `__proto__` member that would enter the script's ABI. A literal `{ __proto__: … }` key in a `t.struct` spec or an `s.return` record is never a key at runtime, so it is handled separately: it is now a type error (the new `NoProtoKey` guard), and when its value is what the record holds (a nested struct type in `t.struct`, a handle in `s.return`), which replaces the record's prototype, they throw at recording instead of dropping it. Any other prototype loses nothing and is accepted as before: a `null` one (`Object.create(null)`, `{ __proto__: null }`) or a class instance is read through its own keys. A primitive value (`{ __proto__: t.uint256 }`) is discarded by JavaScript before evs sees the record, so only the type check catches it. evs's own decoded records (error args, interpreter results) now keep such a key as an own property, and `matchScriptError` only dispatches to handlers the table defines itself, never to inherited `Object.prototype` methods.
