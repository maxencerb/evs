# @maxencerb/evs

## 0.3.1

### Patch Changes

- [#150](https://github.com/maxencerb/evs/pull/150) [`1686fe2`](https://github.com/maxencerb/evs/commit/1686fe21e707ba1d7476804fa077933f23b36e3e) Thanks [@maxencerb](https://github.com/maxencerb)! - `bytesN.asString()` now costs the same gas whatever the word. It used to find the last nonzero byte with a loop, about 67 gas per trailing zero byte: 2,269 gas for an all-zero `bytes32` (a failed `symbol()` read), 2,093 for `'MKR'`. The trim is now branch-free (a fold of each byte onto one flag bit, the lowest flag isolated, one multiply), so `asString()` costs about 140 gas for every word, all-zero included. A word with no trailing zero byte costs 18 gas more than before, and each `asString()` site is 63 bytes larger. Results are unchanged.

- [#155](https://github.com/maxencerb/evs/pull/155) [`11b57a2`](https://github.com/maxencerb/evs/commit/11b57a2363f2f6b7bbd0d813ecfc00c720efe04b) Thanks [@maxencerb](https://github.com/maxencerb)! - `DEPLOYLESS_RESULT_PREFIX` no longer warns for a leading `uint256` or `int256` that cannot start with byte `0xEF`. Such a value has to be at least `0xEF·2^248` (about 1.08e77) for a `uint256`, or below `-2^252` for an `int256`, so amounts and counts never trip it. `compile()` now bounds the bit width of the first returned value over the whole script, loops and `s.fn` calls included. `s.env('chainid' | 'blocknumber' | 'timestamp')`, lengths, `s.balance`, `s.codeSize`, widened narrower integers, and loop counters or running sums of such values no longer warn. A returned literal warns only when its first byte is `0xEF`, which fails every call. A `bytesN` still always warns. A `uint256`/`int256` from a script argument, a call output, a reinterpreted hash, `bitNot`, a signed bit operation or a left shift by a runtime amount also still warns. The warning now carries the `site` of the statement that computes the first returned value, so one amount (a sum of `balanceOf` reads, say) can be acknowledged without hiding the warning for a real hash. Its message is now specific to the type: it no longer calls a `uint256` "a hash 1 time in 256", and it says "an int256" instead of "a int256". Bytecode is unchanged.

- [#148](https://github.com/maxencerb/evs/pull/148) [`e7bfc05`](https://github.com/maxencerb/evs/commit/e7bfc053f5435337e41275a04dc70fd7a50496ea) Thanks [@maxencerb](https://github.com/maxencerb)! - A handle method called without its handle, passed on as a callback (`xs.map(x.add)`, `s.if(done, loop.break)`) or stored and called bare (`const f = x.add; f(y)`), now throws `EvsTypeError` (`TYPE_MISMATCH`) naming the method and the arrow to write instead: `Expr.add was called without its handle … (v) => x.add(v)`. It used to throw an `EvsInternalError` asking to report a bug in evs (`Expr`, `Cell`, `MutArray`, tuple and field handles), or a bare JS `TypeError` (`LoopCtl.break` / `.continue`). A method invoked on another value (`x.add.call(cell, 1n)`) gets the same error, naming what it was called on.

- [#147](https://github.com/maxencerb/evs/pull/147) [`56a24d8`](https://github.com/maxencerb/evs/commit/56a24d823ee08241f8be8fdc4912d632d647f4fc) Thanks [@maxencerb](https://github.com/maxencerb)! - `interpret(script, args, chain)` now reports a wrong argument or chain on the offending value: a number for a `uint256`, a struct missing a member, a missing argument or a chain without `staticcall` reads "Type 'number' is not assignable to type 'bigint'" (or the like) right there. Before, it was "No overload matches this call" on the whole call, led (under TypeScript 7, replaced) by the script "missing the following properties from type 'ScriptIr'". `interpret` is now one signature, generic in the script's ABI, in place of the script and bare-`ScriptIr` overloads. The inferred `args` and `outcome.values` types are unchanged for both kinds of target, and a wrapper generic in its script type (`<S extends EvsScript>(s: S, args: readonly unknown[]) => interpret(s, args, chain)`) compiles as before.

- [#153](https://github.com/maxencerb/evs/pull/153) [`35ff601`](https://github.com/maxencerb/evs/commit/35ff6014aac02f16f8dbe27c68f486a2ce02fc75) Thanks [@maxencerb](https://github.com/maxencerb)! - `mulDiv` / `mulDivRoundingUp` no longer inline the whole FullMath sequence (about 110 bytes) at every site: a script with two or more sites emits it once as a shared subroutine that each site calls, so an extra site costs about 8 bytes and 36 gas per evaluation (about 10 bytes and 61 gas when the script mixes `mulDiv` and `mulDivRoundingUp`). Five `mulDiv` sites shrink from 1,169 to 657 runtime bytes, about 110k less gas in the default deployless mode; a script with a single site compiles exactly as before. Results, Panic codes and `explainRevert` attribution are unchanged.

- [#154](https://github.com/maxencerb/evs/pull/154) [`ce24366`](https://github.com/maxencerb/evs/commit/ce24366133987394e6c6ba206e6d7a3523fe84cc) Thanks [@maxencerb](https://github.com/maxencerb)! - A struct call argument written as an object literal now type-checks with runtime values in it. `args: [{ tokenId: id, recipient, amount0Max: MAX, amount1Max: MAX }]` in `s.read`/`s.call`/`s.simulate` and their `try*` forms failed to compile (TS2769, `Type 'Expr<"uint256">' is not assignable to type 'bigint'`) as soon as a member was an `Expr`, although recording accepted it and sent the same calldata as the `s.tuple(...)` form. The same holds for the elements of a `tuple[]` argument literal and for a struct member given as a literal (in an `s.tuple` init, `Field.set`, `MutArray.set` or an `s.fn` struct argument). A struct literal still names every member (use `s.tuple` to leave members at zero), a tuple with an unnamed member still takes a positional array, and a fixed `tuple[N]` literal still takes exactly N elements. The shapes are exported as `StructLiteral` and `TupleArrayLiteral`.

- [#152](https://github.com/maxencerb/evs/pull/152) [`552f7db`](https://github.com/maxencerb/evs/commit/552f7db377cf4ff742164023cf6222077c9b6c82) Thanks [@maxencerb](https://github.com/maxencerb)! - `toUint` / `toInt` on a non-numeric receiver: the compile error now names the conversion to use first, as the recording-time `TYPE_MISMATCH` does. Since 0.3.0 `addr.toUint(t.uint160)` was rejected by tsc with an opaque "`'this'` context … is not assignable to … `Expr<never>`"; the method's `this` type is now the message itself (`".toUint(): cannot convert from 'address' — the source must be numeric (uintN/intN) — use .asUint160() first (then .toUint(…))"`, and `.asUint()` for a `bytesN`; any other non-tuple receiver gets the recording-time text without a hint, e.g. ".toUint(): cannot convert from 'bool' — …"). - [#151](https://github.com/maxencerb/evs/pull/151) [`73e89bc`](https://github.com/maxencerb/evs/commit/73e89bcc7c5765f96504a1917783831724972969) Thanks [@maxencerb](https://github.com/maxencerb)! - An all-zero or mostly-zero literal (one whose memory image is at least half zero words, such as `s.lit(t.array(t.uint256, 800), zeros)` or an empty `bytes`) can now be a zero-filled allocation plus one store per nonzero word instead of a bytecode data segment that spent 32 bytes on every zero word. A zero `uint256[800]` used to fail with `COMPILE_LIMIT` (25,867 bytes of runtime); it now compiles to 237 bytes, and a zero `uint256[64]` shrinks from 2,314 to 235 bytes. An all-zero literal always takes this form. A sparse one takes it only when it is the smaller code for the whole script: one data segment serves every use of the same literal, so a sparse table recorded in many `s.if` bodies keeps its shared segment. The zero-fill costs the same gas per word as the `CODECOPY` it replaces (+8 gas for an all-zero literal), and each nonzero word of a sparse literal adds about 17 gas for its store, paid every time the literal is materialized (every iteration inside an `s.for` body). `s.newArray(elem, n, { fixed: true })` is the mutable spelling of the same zero array; `s.let` still requires an init.

- [#132](https://github.com/maxencerb/evs/pull/132) [`c66ebb2`](https://github.com/maxencerb/evs/commit/c66ebb2b65a1916e973e84fd8448a46b0e6a5973) Thanks [@maxencerb](https://github.com/maxencerb)! - `s.call`, `s.simulate` and their `try*` forms can now send ETH: pass `value` (a literal or an `Expr<'uint256'>`, in wei) to call a `payable` function with `msg.value`. - [#116](https://github.com/maxencerb/evs/pull/116) [`d5d270d`](https://github.com/maxencerb/evs/commit/d5d270de641bf17f0bf26d770dbed1e6b3f00baa) Thanks [@maxencerb](https://github.com/maxencerb)! - `s.read` / `s.call` (and their `try*` forms) whose outputs are all words (`uint256`, `address`, `bool`, …) no longer keep their returndata in memory. The exception is a call whose arguments need encoder memory, which it still reserves on every call and still warns about (`s.read(f) (call-arg encode frames)`): arguments holding fixed-size arrays, arrays of structs, strings, bytes or arrays, or structs nested three or more dynamic levels deep. Bytecode changes for these call sites: each is a few bytes smaller and cheaper. Reads with a `string`, `bytes`, array or tuple output, and every `s.simulate`, still allocate and still warn.

Also flags `s.simulate` sites with no outputs in a loop, which allocate too.

- [#109](https://github.com/maxencerb/evs/pull/109) [`3fd33b5`](https://github.com/maxencerb/evs/commit/3fd33b555bf6b2d811d2d08ab161164d8be9cfab) Thanks [@maxencerb](https://github.com/maxencerb)! - Tuple literals now follow abitype and viem's naming rule everywhere: a literal is an object keyed by member name only when every member is named, and a positional array as soon as one member is unnamed (an empty `name`, or no `name` key at all, as viem's `parseAbi` emits). This applies to `s.tuple` inits, `Field.set`, `Cell.set`, `MutArray.set`, call arguments (overload resolution included), `s.fn` arguments, `tuple[]` literal elements and `s.throw` arguments, at the type level and at recording alike. Before, a partly named tuple (common in `t.fromOutputs` of a verified ABI, such as `returns (uint256 amountOut, uint256)`) was typed positionally in call args and returns (viem) but as a name-keyed record in `s.tuple` inits, and recorded only as a name-keyed record, so its unnamed member was silently zero. **Behavior change:** `s.tuple(T, { amountOut })` for such a tuple now throws; write `s.tuple(T, [amountOut])`.
  
  Shapes that used to be accepted or ignored now throw `TYPE_MISMATCH` at recording:
  
  - a struct literal key that names no member (before, the intended member silently stayed zero);
  - an element past the last member of a positional literal;
  - an index-keyed record such as `{ 0: x, 1: y }` for a fully unnamed `t.tuple` (before, it was read positionally); write the array `[x, y]`;
  - a `Cell`, `Field` or `MutArray` handle where a tuple is expected (before, it became an all-zero tuple; read it with `.get()`);
  - a `Tuple` or `Expr` handle as an `s.tuple` init (before, an all-zero tuple); pass the handle itself where the tuple is expected.

- [#50](https://github.com/maxencerb/evs/pull/50) [`9ac1c5e`](https://github.com/maxencerb/evs/commit/9ac1c5e59635eb3bb182dda28b2d09d491430212) Thanks [@maxencerb](https://github.com/maxencerb)! - Add a liveness-based frame allocator behind `compile(script, { optimize: true })` ([#41](https://github.com/maxencerb/evs/issues/41)). With `optimize` on, codegen computes a live range for every value over the linearized statement order and linear-scans the static frame, so a value takes over the slot of one that is dead — long chains of temporaries collapse to a slot or two, and the frame (hence memory-expansion gas for every later allocation) shrinks. - [#49](https://github.com/maxencerb/evs/pull/49) [`f1a69b0`](https://github.com/maxencerb/evs/commit/f1a69b02b61e1dece81d6384685e454276210a94) Thanks [@maxencerb](https://github.com/maxencerb)! - Add an opt-in peephole optimizer behind `compile(script, { optimize: true })` ([#39](https://github.com/maxencerb/evs/issues/39)). - [#47](https://github.com/maxencerb/evs/pull/47) [`94627ac`](https://github.com/maxencerb/evs/commit/94627ace998caf35d42efca1e48d8318fa6addae) Thanks [@maxencerb](https://github.com/maxencerb)! - `s.simulate` follow-ups ([#36](https://github.com/maxencerb/evs/issues/36)):
  
  - **`gas` on the simulated target.** The optional `gas` cap of `s.simulate` / `s.trySimulate` now bounds the _inner_ target `CALL` (it used to cap the self-call hop). The trampoline wire header grows a gas word — `[trampSel(4)][target(32)][gas(32)][calldata]` — and the hop itself always forwards all gas, so a gas-hungry target surfaces as a failed dry-run (`success = false` / an empty revert) instead of starving the trampoline. `s.call` / `s.read` caps are unchanged; the 63/64 rule is documented.
  - **Nested simulate is documented and pinned.** Simulate sites compose (inside `s.fn` bodies, one dry-run feeding the next) — new differential and anvil tests cover it.
  - **Sender mode.** `toViem({ mode: 'stateOverride', sender })` installs the script _at_ `sender` and sets `account: sender`, so every sub-call target — including a simulated write — sees `msg.sender = sender`. `toViemStateOverride` takes the same `sender` option.
